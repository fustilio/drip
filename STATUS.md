## Known limitations (accepted, not bugs)

- Slice correspondence (M2) is keyed by symbol composition, not diff content — see `docs/adr/0006`. A slice whose touched symbols change identity loses its PR link.
- Def-use edges are name-only regex matching, not scope-aware reference resolution (`planner.ts`, flagged inline).
- Override selectors break silently on symbol rename/move — no fuzzy relocation until M4's anchor system (`docs/adr/0004`).
- `git apply` per-slice ordering has only been tested against well-separated hunks with unique context; a pathological near-duplicate-context case could still trip fuzzy matching.
- Squash-merge detection is a reverse-apply-check against the base branch's current tip, not real content-addressing — it can false-negative (fail to detect) if surrounding context drifted, but won't false-positive silently drop a slice that wasn't actually merged (a failed reverse-apply just means "not detected," the slice still pushes normally).
- Comment anchoring only reconciles on pushes where the slice's content actually changed (piggybacks on the M3 content-hash check) — a comment posted on a slice that never gets touched again is never checked, which is fine (nothing to reconcile), but a comment posted then immediately squash-merged away is never reconciled either since squash-merged slices skip the push path entirely.
- Only top-level, right-side (`side: RIGHT`) review comments are considered; left-side (deleted-line) comments and thread replies are silently skipped rather than reconciled — see `docs/adr/0007`.
- Build-cache skip is prefix-based, not true DAG-independence — see `docs/adr/0008`. An edit near the *start* of the stack still forces a full rebuild of everything after it, even slices with no real relationship to the edit.
- `drip push` materializes atomic slices or manifest projections; `--coarsen` remains a planning mode and is still rejected on `push` (see `docs/adr/0017`). Pushing *coarsened* projections directly is still not supported — with `--manifest` (docs/adr/0018) covering the case that actually matters, it may never need to be.
- Flat-first, `--manifest` and `manifest adopt` have been exercised against real git (with GitHub mocked or stubbed) and by hand through the CLI, but none has been run live against real PRs the way stacked mode was — the `blocked` and prerequisite-widening paths in particular are defensive and have not fired on a real branch.
- Adoption's tree comparison replays the adopted branch's diff onto the mega branch's merge base, so a handcrafted branch cut from a much older base can fail to replay (context drift) even when its content is right. That's reported as `adopt-replay-failed` with "rebase and try again" rather than being worked around — a fuzzy match here would be the one heuristic this command exists to avoid.
- An adopted PR whose base disagrees with the manifest graph is reported on every push and never retargeted, by design. Nothing yet reconciles the *other* direction — a base someone changes on the PR is only picked up when `manifest adopt` is re-run.
- `drip push` cannot be exercised live from an agent environment without the `gh` CLI — `github.ts` shells out to it in eight places. Verifying flat-first, `--manifest` or `manifest adopt` against real PRs needs a shell that has `gh` authenticated.
- `parseDiff` still cannot *slice* binary, rename-only, mode-only or empty-file diff sections — they are absent from every slice and will fail the tree-hash invariant. As of issue #12 they are no longer silent: they're reported by path and reason, and named in the failure they cause. Handling them properly (a rename is a real reviewable change) is still not done.

## Bugs found via real usage (GitHub issues #1, #2), fixed

- **Worktree support** (issue #1) — `openStore` hardcoded `<repoRoot>/.git/drip.db`, which broke in linked worktrees (`.git` is a pointer file there, not a directory). Fixed via `git rev-parse --git-path drip.db`, which resolves to the worktree's private gitdir — see `docs/adr/0011-drip-db-location.md`. Regression test: `src/store.test.ts`.
- **Global-install WASM resolution** (issue #2) — grammar `.wasm` paths were resolved relative to CWD (the target repo being planned), so a globally-installed `drip` only worked if the target repo happened to have drip's own tree-sitter deps installed. Fixed via `createRequire(import.meta.url).resolve(...)`, resolving relative to drip's own install location instead — see `docs/adr/0012-wasm-asset-resolution.md`. Not yet covered: a `bun build --compile` single-binary distribution (no `node_modules` to resolve into at all) — flagged, not fixed, out of scope for this pass.
- **Cycle diagnostics** (issue #3) — a cyclic slice DAG used to collapse to a bare `"dependency cycle in slice DAG"` error with no detail. `plan`/`plan --json` (and `drip_plan`/`drip_verify` over MCP) now report each strongly-connected component: member slices, participating edges with symbol/file/line evidence on both sides, and any existing override already touching the cycle. Diagnostics only — no auto cycle-breaking, `plan.order` is still `null` and `verify`/`push` still refuse to proceed. See `docs/adr/0013-cycle-diagnostics.md`.
- **Fallback grouping** (issue #7) — every hunk tree-sitter couldn't place went into one global `ungrouped` slice: on a real branch that was 170 hunks across 48 files with 25 prerequisites, mixing lockfiles, manifests, tests, docs, config and route wiring into the largest PR in the plan. Unassigned hunks now get a deterministic per-path group key (`<path>::(file)`, or `<dir>/package.json::(deps)` for a manifest and its lockfile) and run through the same union-find and the same `force_merge`/`force_split` mechanism as symbol groups — no second override system. Each carries the reason it's unassigned, reported per hunk and per group in the text plan and `--json`. Slice signatures now key off the planner's group key for every hunk instead of a `file::?` placeholder, so a fallback group's correspondence survives replanning. See `docs/adr/0015-fallback-grouping.md`.
- **Flat-first projection** (issue #6) — `drip push` stacked every slice onto the previous one, so a DAG with 66 independent roots became a 114-deep serial review chain. `--projection flat-first` picks each base from the DAG (root → base branch, one prerequisite → that branch, several → a generated integration branch whose tree is the prerequisite closure); `--projection stacked` stays the default. Flat-first is the first thing here that applies a *subset* of slices, so a slice that won't apply on its DAG prerequisites has them widened once, deterministically, to the earlier slices touching its files — reported, not hidden — and if it still won't apply it's reported `blocked` and push exits 1. This also corrected what `unchanged` means: the content hash now covers the slice's patch, the tree its branch resolves to, and the ref it targets, fixing a latent stacked-mode bug where editing an early slice left every later branch un-pushed. See `docs/adr/0016-flat-first-projection.md`.
- **Review-sized coarsening** (issue #8) — 114 atomic slices were the right technical ordering and the wrong PR plan. `plan --coarsen` / `verify --coarsen` (`src/coarsen.ts`) group slices into candidate projections via four deterministic non-AI rules (`same-file`, `test-affinity`, `sole-consumer`, and budget-driven `directory-affinity` under `--target-slices n`), rejecting any merge that would make the projection graph cyclic. Each projection reports its constituent slices, external prerequisites and why each merge happened; `force_split` is never coarsened away and a budget that would need it is reported unmet. Needed no new verifier — a coarsened plan is handed to the existing tree-hash and build checks in the shape they already consume. `push` still materializes atomic slices and rejects `--coarsen` rather than verifying one thing and pushing another. See `docs/adr/0017-review-sized-coarsening.md`.
- **Semantic projection manifest** (issue #9) — running the above on a real branch produced 161 atomic slices, and `--coarsen --target-slices 12` met the count by folding 149 of them into one projection. Two separate problems, fixed separately. (a) A **defect** in coarsening's budget pass: it always merged into a bucket's first member, so the budget was met by growing one runaway. Now it pairs the two smallest, caps any projection at twice its fair share, and reports a budget as unmet-with-a-reason rather than degenerate. (b) A **limit of the approach**: even balanced automatic grouping can't recover "the report-tab detail experience" — that's product intent, not graph structure. So `src/manifest.ts` adds a versioned JSON manifest, proposed outside drip and validated deterministically inside it: every slice assigned once or deferred with a reason, nothing deferred that another projection needs, acyclic `dependsOn`, every atomic dependency crossing a boundary declared (widening fine, dropping not), each projection actually applying on its declared prerequisites, glue reachable from every referrer, review budgets, and the whole graph reconstructing the tree hash with deferred slices included. `drip validate-plan` and `push --manifest` (plus `drip_validate_plan` over MCP). A projection's PR is keyed on its manifest id, making it the first genuinely durable correspondence identity in drip — replanning underneath a projection no longer costs it its PR. See `docs/adr/0018-semantic-projection-manifest.md`.
- **Executable verification** (issue #10) — a projection's `verification` commands were metadata: printed, copied into the PR body, never run. But a projection can apply cleanly and reconstruct the final tree while still failing its own typecheck or targeted test for missing operational glue (a fixture, an export, route wiring), and "each PR is independently runnable" is the whole claim a semantic projection makes. `src/verification.ts` now executes each projection's commands in a throwaway worktree at that projection's own materialized commit, gating both `validate-plan` and `push --manifest`. Cached by the tree the command ran against and only on success; sequential rather than concurrent, since these are arbitrary user commands that bind ports and share fixtures, unlike the compiler the per-slice build check runs. Output goes to `<gitdir>/drip/verification/<branch>/` and is reported by path. An empty `verification` warns unless `verificationReason` is set; `--strict` promotes warnings to errors for CI, `--no-manifest-check` skips execution. See `docs/adr/0019-executable-verification.md`.
- **Adopting existing PRs** (issue #11) — `push --manifest` could maintain PRs drip opened and nothing else, so a team that already had good, small, handwritten PRs had to choose between abandoning that review context and not using drip for the integration workflow. `drip manifest adopt` (`src/adopt.ts`) binds one semantic projection to one existing PR: projection id, PR number and head branch all required and cross-checked, and correspondence recorded only when the branch's effective diff, replayed onto the mega branch's merge base, produces exactly the projection's materialized tree — refused otherwise with an interdiff, and with "carries its own change but not its prerequisite closure" called out by name rather than left to be read out of a diff. Adoption touches nothing remote. Afterwards `push` treats the branch as someone else's property: `--force-with-lease` against the recorded sha (a reviewer's commit blocks the push instead of vanishing), skip-on-tree-equality instead of skip-on-content-hash, and no retargeting — a base disagreeing with the manifest graph is reported every run. Branch names now resolve through correspondence, so a dependent's base names its prerequisite's *adopted* branch. `manifest list`/`manifest forget` inspect and undo bindings. See `docs/adr/0020-adopting-existing-prs.md`.
- **Worktree as a diff source** (issue #12) — `plan` diffed committed history only, so an in-progress refactor was invisible and drip couldn't propose a review partition until after the commits it was supposed to inform. `--worktree` on `plan`/`verify` (`src/source.ts`) substitutes the diff source and nothing else: HEAD's tree with every non-ignored change staged on top — staged, unstaged and untracked — written with `git write-tree` in a scratch index, so the repo's index and working tree are untouched and everything downstream consumes an ordinary tree object. The plan stays base-relative (slicing only the uncommitted delta would produce slices that don't apply on the base) and keeps the branch as its identity, so overrides and an emitted manifest carry over unchanged once the commits exist. The source is reported on every run — a clean worktree says it planned committed history rather than letting the reader assume otherwise — and `push`/`--assign-ids` are refused in worktree mode. Also closes the long-standing silent `parseDiff` drop: binary, rename-only, mode-only and empty-file sections are now `plan.excluded`, printed in an EXCLUDED block, carried in `--json`, and named in any tree-hash failure they cause. `drip_plan`/`drip_verify` take `worktree` over MCP. See `docs/adr/0021-worktree-as-a-diff-source.md`.
- **Local materialization and draft PRs** (issue #13) — every code path that produced a projection's actual commits lived inside `push`, which force-pushes branch heads and opens PRs in the same breath, so there was no way to *look at* a projection first. That's the wrong order for the workflow the manifest exists to serve: splitting an integration branch into a hand-reviewed PR set means comparing an intended projection against branches that already exist — often handwritten ones with reviewers on them — and reconciling the scope disagreement before anything is adopted or force-pushed. `drip materialize` (`src/materialize-local.ts`) runs the same validation as `validate-plan`, then the same `materializeFlatFirst`/`materializeSliceCommits` `push` uses, and stops at the local repository: a ref per projection under `drip/<branch>/<id>` and, with `--output dir`, a worktree per projection — no remote ref, no `gh` call, no correspondence recorded. `--only id[,id]` materializes a subset without narrowing what it's built on (the prerequisite closure comes with it, reported as such). Re-running is a no-op judged by tree, not by sha, since `commit-tree` mints a fresh sha every run; a ref holding different content is reported `blocked` and left alone until `--force`. An adopted projection still materializes to drip's own ref and reports the binding, because overwriting a local copy of someone else's branch is the accident the command exists to prevent. `--projection` defaults to `flat-first` here (unlike `push`) since a manifest's `dependsOn` graph *is* the flat-first base selection. Separately, `push --draft` opens drip-owned PRs as drafts — creation only: an existing PR, drip's own or adopted, keeps its state and the result says why, since marking a PR ready for review is a decision a re-run must not undo. `PushResult.draft` is three-valued so dry-run can report the state it *would* open with. Building this also surfaced a latent bug from issue #12: `validateManifestAgainstGit` compared the projections against the *branch tip* rather than the plan's diff source, so `validate-plan --worktree` failed the tree-hash invariant on any dirty tree. It now takes `sourceRef` (and passes `plan.excluded` through, so the failure names its cause) — regression test in `worktree.test.ts`. See `docs/adr/0022-local-materialization-and-draft-prs.md`.
- **NUL bytes in source** — `coarsen.ts` and `push.ts` each carried a literal `U+0000` where a string separator was intended. The code worked (a NUL is a fine separator at runtime) so no test caught it, but git and grep both treat such a file as binary: `git diff` reported `Bin 6388 -> 10367 bytes` instead of a patch. Found by noticing the diffstat, not by a test. Worth remembering that "tests pass" says nothing about whether a file is reviewable.
- **Def-use false cycles** (issues #4, #5) — two shapes of false cross-file edge in the name-only def-use matcher. (4) Every changed constructor's own declaration contains the literal word `constructor`, so any two changed constructors always false-matched each other regardless of actual usage — fixed by keying constructors by their enclosing class name instead. (5) Same-named unexported local helpers in different files (e.g. `renderSection` in two test files) created a spurious cross-file edge — fixed by gating cross-file def-use matches on the definition being `export`ed; same-file matching is unaffected. See `docs/adr/0014-def-use-edge-precision.md`.

## Gotchas hit during this build (so they don't get rediscovered)

- Bun's `execFileSync` inherits stderr live by default, unlike Node's pure pipe-and-capture — every git failure double-printed raw `fatal: ...` noise until `stdio: ["ignore","pipe","pipe"]` was forced explicitly (`git-backend.ts`).
- `git commit-tree` doesn't inherit author identity and isn't idempotent by default — every call mints a fresh SHA with the current user as author unless `GIT_AUTHOR_*` env is passed through explicitly (`change-id.ts`).
- TypeScript 7.0.2's control-flow narrowing doesn't reliably track mutations of an outer `let` from inside a nested closure — a mutable object box sidesteps it (`planner.ts`, `findQualifiedSymbol`).
- A fresh `git clone` only checks out the default branch; other branches need an explicit `git checkout` before drip can diff them — not a drip bug, just how git works, documented in the README.
- Windows needs a junction, not a plain symlink, for the `node_modules` shortcut into each per-slice build-check worktree (`verify.ts`).
