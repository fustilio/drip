# Def-use edges: key constructors by class, gate cross-file matches on export status

The def-use matcher (`planner.ts`) infers a slice dependency edge whenever a changed hunk's text contains the literal leaf name of another changed hunk's definition — a deliberately crude, name-only heuristic (flagged as a known limitation from the start, not scope-aware reference resolution). Two real false-cycle cases from that crudeness were reported and fixed here.

**Issue #4 — constructors.** Every class constructor's qualified symbol ends in the leaf `constructor`. Keying `definersByName` by that bare leaf meant any two changed constructors collided: declaring a constructor requires literally writing the word `constructor`, so each constructor's own hunk text always self-matched every other changed constructor's definer entry — a guaranteed false edge in both directions the moment two classes' constructors changed in the same diff, independent of whether either actually referenced the other. Fixed via `defUseKey()`: a constructor is now keyed by its **enclosing class name** instead of the word `constructor` — `Service.constructor` becomes the def-use key `Service`, which is what a caller actually writes (`new Service()` or a type-annotated parameter), not the ubiquitous keyword.

**Issue #5 — unexported local helpers.** Two unrelated files can each declare a private helper with the same conventional name (`renderSection`, common in test files) — the matcher had no way to tell "same name, unrelated" from "same name, actually imported." Fixed by tracking whether each hunk's top-level declaration is `export`ed (`findQualifiedSymbol` now also walks up through `lexical_declaration`/`variable_declaration` wrappers to check for an enclosing `export_statement`), and gating the def-use match: a cross-file candidate (`a.file !== b.file`) is only accepted if the definition side is exported. Same-file matches are unaffected — the existing heuristic already has enough locality within one file to remain useful as-is.

**Not covered, by design:** `export { foo }` named-export lists (would require tracing a separate identifier back to its local declaration — a real scope-aware pass, not a one-line fix) and `import { foo as bar }` aliasing. Both remain under the existing "def-use is name-only regex matching, not scope-aware reference resolution" limitation (STATUS.md) — this ADR narrows two specific false-positive shapes, it doesn't promote the matcher to a real reference resolver.
