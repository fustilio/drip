# M5 AI conveniences: expose data for external tools, don't bundle a provider

The plan's M5 scope names three AI-assisted spots (slice naming, fuzzy comment relocation, boundary suggestions), all behind an `--ai` flag with a bundled model call. Explicit user decision during M5: don't build that. Instead, make the data those three spots need available to whatever external tool the user already has (an agent, a hand-rolled script, eventually maybe an MCP server) — drip stays a deterministic CLI with zero model dependency, network calls, API keys, or cost controls in its own process.

This isn't a smaller version of the plan's M5 AI scope — it's a different shape for the same goal, and it's actually closer to what §9 already argued: **"the AI in this workflow isn't in the tool. It's upstream."** A bundled `--ai` flag puts a model inside drip's process, which is exactly the boundary §9 says shouldn't be crossed. Keeping AI entirely external and having drip expose read-only structured data (`drip plan --json`) that a human-directed agent can read, then write decisions back through the *existing* deterministic mechanism (`drip override add`), satisfies "AI proposes, determinism disposes" without drip ever importing a model SDK.

What this gets, concretely, per plan spot:
- **Slice naming / PR descriptions**: `drip plan --json` gives an external tool the files/symbols/hunks per slice — enough to generate a name or description. Nothing in drip generates or applies it; that's still manual/PR-editor today.
- **Boundary suggestions**: `--json`'s `unmatchedOverrideSelectors` and per-slice symbol lists are the same ambiguous-boundary signal a human reviewing `drip plan`'s text output already gets. An agent reading it can propose `drip override add`, but the override is still a deterministic, durable, human-visible fact the moment it's recorded — same guarantee as if a human typed the command themselves.
- **Fuzzy comment relocation**: not exposed yet. M4 already orphans loudly (`docs/adr/0007`) rather than guessing; there's no read/write surface for a fuzzy suggestion yet since nothing consumes it. Revisit if orphaned-comment volume in practice makes tier-1-only unacceptable — the trigger is the same one named in ADR 0007, not a separate decision.

Known gap: an MCP server (or similar) is not built. `--json` is the minimum useful surface — a protocol wrapper around it is straightforward to add later and was explicitly deferred as premature (no MCP client has asked for it yet; CLI + JSON already gives any agent that can shell out full access).
